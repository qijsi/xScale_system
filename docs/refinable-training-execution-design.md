# xScale：面向调优决策的可精化训练执行图

日期：2026-10-27。状态：研究设计与论文主线，不是已实现系统或已完成实验的声明。

## 1. 核心问题与一句话 idea

大模型并行调优需要比较大量候选策略。完整训练昂贵；小集群仿真虽然降低了所需 GPU 数量，但逐个候选重复捕获、初始化和执行整个深层模型，仍可能使评测成为搜索瓶颈。

**在保留完整模型与目标集群逻辑执行语义的前提下，将真实执行需求压缩到少量具有明确适用上下文的代表性层段，再针对影响策略选择的歧义按需展开。**

小规模仅指调优平台的物理资源。模型深度、隐藏维度、序列长度及目标集群的逻辑 rank、通信组和并行配置不因此缩小。该方法评估训练性能与容量可行性，不声称压缩执行产生与完整训练相同的权重、梯度或收敛轨迹。

建议论文题目：**xScale: Decision-Directed Emulation for Efficient LLM Parallelism Search**。

## 2. 两层目标如何统一

训练目标：在固定模型、训练语义、目标平台和有效 batch 下，选择满足每个目标 rank 显存容量约束、吞吐量最高的策略。改变 microbatch 时必须相应调整梯度累积，或明确标记为另一种训练任务。

系统目标：在有限的小平台评测预算内，尽快选出目标系统上的高质量可行策略。把搜索开销分为候选生成与评测成本；本文主要研究后者，同时保留搜索算法作为必要组件和对照。

评测成本依赖已积累的证据 K：C_eval(s | K)，而不是策略固有的固定价格。共享摘要可以减少重复 profiling；新上下文也可能使旧摘要失效，因此不承诺评测延迟随样本数单调下降。

主要结果应是“相同评测预算下最终策略的目标吞吐量”和“达到给定质量所需的总墙钟时间”，辅以 GPU-hours、显存错误可行判断和单次评测延迟。不能仅报告候选数量或 cost model 的平均误差。

## 3. 统一抽象：可精化训练执行图

完整逻辑图 G_s = Plan(M, s, H) 描述某个候选策略在完整目标集群上的执行。图包括 forward、backward、recompute、optimizer、microbatch 调度、通信组及放置，以及参数、梯度、优化器状态和激活的存储生命周期。

逻辑图与物理求值计划分离。同一段逻辑执行可以由结构摘要、测量摘要或真实层段窗口求值；精化只改变求值分辨率，不改变模型和策略。图可以用模板与重复计数紧凑表示，但所有层位置、跨段依赖和存储身份必须可恢复。

摘要不是单一的“层耗时”，而是一个带适用条件的边界转换：

`(入口就绪事件，入口存活存储，上下文) → (出口事件，分配/释放及生命周期效应)`。

摘要还保存来源、版本、重复次数、测量样本、经验残差和失效条件。最小上下文包含 shape、dtype、GPU/内核后端、TP 切片、F/B/重计算模式、流水线位置与阶段、梯度 bucket 边界及并发通信模式。相同层类型不自动具有相同性能。

三个操作：

- `Summarize(segment, context, evidence)`：生成结构或测量摘要，返回适用域；缺证据则标记 unknown。
- `Evaluate(graph, realization, budget)`：组合目标时间与显存轨迹，同时记录实际评测时间、GPU 占用和证据来源。
- `Refine(region, reason, budget)`：拆分上下文或扩大真实执行窗口，更新摘要，并使依赖旧摘要的候选结果失效或重算。

可实现性边界：第一版从静态 dense decoder、固定后端与拓扑、支持的 TP/DP/PP 和重计算配置开始。动态 MoE 路由、异构网络以及任意算通融合需要独立证据，不在第一版泛化保证中。

## 4. 三项核心贡献

### C1：上下文感知的执行折叠与组合分析

研究“哪些层段可以共用证据，以及证据何时失效”。从完整逻辑图识别重复结构，在边界一致且上下文相容时折叠；保留层位置、bucket ready 事件、流水线首尾与预热/稳态/排空阶段。不同配置只复用相容的子图摘要；microbatch、TP、重计算或 bucket 配置变化可能要求重新捕获。

技术产物是折叠条件、边界组合规则、失效传播与失败回退机制，而非仅定义一个 IR。不能把已有的“重复层只 profile 一次”重新命名为创新：vTrain 已利用重复层减少 profiling，FlexFlow 已有缓存与增量模拟，dPRO 已有 partial replay 和 symmetry。新增价值必须来自对上下文、时间和显存影响的可验证处理，并体现在策略选择质量上。

### C2：时间与显存一致的摘要执行运行时

研究“省略真实执行后，如何仍能组合目标性能和容量行为”。运行时维护目标逻辑时间与物理评测墙钟时间；代表性窗口产生真实测量，摘要通过依赖驱动的调度组合目标时间。省略段不能用同等时长 sleep 代替后再宣称墙钟加速；收益必须来自真实减少 capture、初始化、重复 profiling 或求值工作。

显存采用完整逻辑状态账本，每层仍有独立参数与状态身份。目标峰值按存活生命周期计算，不能以采样层数量缩放。需覆盖多 microbatch 激活、梯度 bucket、临时 workspace、别名与通信缓冲。实际 allocator、碎片和框架外分配另行测量；抽象字节数低于容量不等于已经证明不会 OOM。

对于可能改变决策的峰值窗口或重叠区间，扩大真实执行范围进行验证。代理执行必须分别验证时间依赖和资源竞争；计时等待不代表 SM/HBM/cache 竞争。若无法在小平台复现所需上下文，则标记 unsupported/unknown，使用更保守的区间、扩大验证平台或保留未决候选，不能伪造可行性。

### C3：面向策略选择的渐进精化

研究“下一个测量应落在哪个候选的哪个上下文”。采用简单候选生成器，维护一个已验证 incumbent 与少量 contenders。粗摘要先筛掉明显较差的候选；仅在吞吐排名接近、显存接近边界或适用域不明时精化相应层段与交互邻域。测量更新可同时改善多个共享该摘要的候选。

不需要复杂 BO 或全局 trust 模型。首版可按“是否可能改变 incumbent、是否影响可行性、测量开销”排序精化动作。区间使用独立验证数据估计误差，并显式声明经验性；未经校准的区间不构成概率保证，单个区间也不能直接推出整个自适应搜索正确。最终验证必须计入预算，预算不足则返回带未决状态的最佳已验证策略。

## 5. 简化的 cost model

通信、计算、显存是解释策略结果的三个维度，不分别设计三个复杂优化器。

| 项目 | 首版机制 | 用途 |
| --- | --- | --- |
| 计算 | 按上下文缓存代表性层段的 F/B/重计算测量 | 给摘要赋时，发现复用失效 |
| 通信 | 按通信组、拓扑和消息区间拟合启动项与有效带宽；必要时测真实重叠窗口 | 组合 ready/completion 事件，保留逻辑通信数量和顺序 |
| 显存 | 完整状态解析计数＋测量的激活/workspace＋生命周期事件 | 判断每个 rank 的容量风险并定位峰值窗口 |

总耗时来自调度图关键路径，不能简单将通信时间与计算时间相加。benefit 用相对同一基线的目标吞吐提升和峰值显存变化表达；显存首先是容量约束，目标仍是吞吐量。随证据积累更多复用测量摘要；是否引入额外学习模型由 held-out 精度与评测成本收益决定。

## 7. 最小 motivation 与贡献实验

先固定完整模型与目标逻辑拓扑，控制变量只改变评测实现。代表性数量可以从每个相容上下文 1、2、4 段到全部，数字是 sweep 设置，不是实验结果。异质上下文数量决定下限，不能预设全模型一段足够。

| 实验 | 要回答的问题 | 核心对照与输出 |
| --- | --- | --- |
| M1：重复评测开销 | 小平台仿真是否仍受全深度重复工作限制？ | 固定模型/策略；分解 capture、初始化、执行、分析，记录冷/热缓存墙钟与 GPU-hours |
| M2：折叠与排序 | 少量层段能否区分策略，何时失效？ | 完整执行、完整小平台仿真、单层 lookup、上下文摘要；报告成对排序/Top-k、近 OOM 错误接受与拒绝 |
| M3：选择性精化 | 不确定性是否集中在少数影响决策的上下文？ | 相同测量预算下均匀增加窗口、固定高精度、决策精化；报告最终吞吐与 time-to-quality |

贡献评估对应 C1/C2/C3 做三组消融：去上下文；去时间/生命周期一致性；去决策精化。再与算子缓存＋全图模拟比较，防止收益仅来自已有 caching。测试 near-tie、bucket 边界、PP 首尾、重计算、长序列等失败场景；第一版范围外配置明确列出。

目标完整执行 F 是最终性能参考；完整小平台 CrystalLLM 执行 C 是继承后端；折叠执行 L 是本系统。分别报告 C 对 F、L 对 C、L 对 F 的误差，不能把 C 当成独立真值掩盖继承误差。完整目标验证不足时收缩评估范围，并明确外部有效性限制。

质量目标以测得 oracle/最好已验证策略为参照，报告有限候选集覆盖范围。时间包含离线 profiling、缓存构建、初始化、搜索和最终验证；冷/热启动分报。任何未达到的质量门槛均报告为未达到，不能从 time-to-quality 曲线删除。

## 8. 实现状态与分阶段里程碑

截至本次文档合并：S1、witness 规划和 synthetic orchestrator 已存在；S2/S5 仍是 stub。新的可精化执行图、生命周期账本、摘要运行时和决策精化控制器尚未实现。2026-10-25 的 85 项测试是旧原型的历史单元测试记录，不是新机制的验证。

1. 建立完整执行和完整小平台仿真的可重复 oracle，先完成 M1；若评测开销主要不在拟压缩部分，则调整方案。
2. 在静态 dense decoder 上实现边界事件与状态账本，执行 M2；先证明少量上下文能保持必要排序和容量判断，再扩展范围。
3. 将真实窗口接到 CrystalLLM；记录两种时间、真实资源消耗、摘要失效，完成 C2 消融。
4. 使用简单搜索器实现 contender 精化与预算内终验，完成 M3 和端到端评估。

不再以补齐 RSS 命名、增加 40 条规则或设计更复杂 BO 作为优先里程碑。OSDI 分量取决于新的机制、真实可运行系统、相对于强基线的量化证据及失败边界，而非抽象和贡献名称的数量。

## 9. 参考与创新边界

- [vTrain，§III-C](https://arxiv.org/html/2312.12391v2)：重复层减少 profiling 已有先例。
- [FlexFlow](https://arxiv.org/abs/1807.05358)：搜索与执行模拟是已有基础，应比较缓存/增量机制。
- [dPRO](https://proceedings.mlsys.org/paper_files/paper/2022/file/b422680f3db0986ddd7f8f126baaf0fa-Paper.pdf)：全局通信图、partial replay 和 symmetry 属于紧邻基线。
- [CrystalLLM 官方实现](https://github.com/AlibabaResearch/CrystalLLM)：继承的 capture/plan/emulate 后端与支持边界。
- [Galvatron](https://arxiv.org/abs/2504.21411)：已有 profiler/search/runtime 体系，应与其搜索目标区分。
- [OSDI 2027 CFP](https://www.usenix.org/conference/osdi27/call-for-papers)：问题意义、原创机制、实用性与正确性均需证据支撑，当前文档不构成录用判断。
